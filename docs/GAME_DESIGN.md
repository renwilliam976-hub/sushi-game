# 寿司小店：玩法需求

## 产品方向与画风

主要面向 iPhone 的寿司制作经营游戏。当前界面方案采用横屏，把厨房和顾客放在同一画面。单机、离线及横屏作为当前工作建议，实际工程方案中应保持可调整。

已选美术方向是简洁日系动画：清晰线条、适量棱角、克制木色与靛蓝，不做过度圆润、光滑的玩具质感。画风与构图参考在 `assets/00_Concepts`。角色要有明显年龄、身形、衣着与神态差异，包括身形宽厚的男性女仆装 cosplayer、中年疲惫上班族、日本小学生、中国游客。不能只给普通角色换衣服。

## 场景与布局

顾客及订单位在上方，食材盒在中间，切配工作台位于食材盒下面。煮饭和补料在一侧，饮料设备在另一侧。新机器买到或解锁后才显示。扩充新食材时增加或开放食材位置，避免让操作区挤到无法点按。当前 2×4 食材位属于布局建议，可根据屏幕调整。

所有可操作对象需有清晰触控反馈；贴图外观与触控热区分别定义。装饰不可遮住操作对象。

## 制作流程

米饭煮熟→海苔铺到竹帘→铺米饭→添加配料→卷寿司→切成成品→交付订单。初期添加一个配料需要点 3 次；购买对应升级后减为 2 次，再减为 1 次。次数属于制作逻辑，制作状态在工作台表现。

食材盒不显示添加进度，也不显示剩余份数。库存只用满、约 75%、约 50%、约 25%、空五档贴图表达。库存内部仍需要准确计量。

配方应按食材组合匹配，以便未来扩充寿司菜单；不要把所有组合写死在界面代码里。

## 出餐、满意度与收入

每位顾客有满意值。完全正确的订单是 100%；错误订单也依据满意度付款。出餐快有额外小费。具体错误权重和小费阈值尚未定，应配置化。快慢影响小费，正确订单满意度保持 100%；额外等待惩罚不是已确认要求。

用户仍在考虑将整份餐放上托盘后一口气交付，还是每个物品分别拖过去。工作建议是先用托盘整单交付，但不是已确认决定。首版可按此暂定，保留交付模块独立以便更改。

结算逻辑要保证一份订单只付款一次。错单处理方式需要与满意度付款一致，不能自行恢复以下已删除规则：

- 卷起前撤回最后一次添加的馅料。
- 交错顾客后盘子自动回到出餐区，并提示需要的配方。
- 错成品留给匹配订单，或按原提议回收重做且只消耗米饭。

## 补料

玩家点击补料口→卡车倒车到店边→后备货厢朝向店门打开→点击货物，货物直接飞入对应食材盒→本波补满后卡车自动离开。

初期通过连续点击补料；后续可购买一键自动补料升级。卡车停靠、货物入盒及离开都要有短而清楚的反馈。费用、是否同时补多种食材、补料耗时、能否中途追加需求尚未定；不得擅自设定额外罚款。

## 升级与经营

| 升级方向 | 用户要求 |
|---|---|
| 配料效率 | 添加一次配料的点击数 3→2→1 |
| 铺海苔／铺饭 | 后期提供自动设备 |
| 卷寿司／切配 | 后期提供自动化或效率升级 |
| 米饭 | 缩短煮饭时间 |
| 菜单 | 解锁更多寿司与所需食材 |
| 饮料 | 购买茶机、啤酒机及清酒供应 |
| 补料 | 手动点击升级为一键自动补料 |
| 装修 | 提供一定数量可选择的装修物件，各自有不同豪华值 |
| 扩展品类 | 后期加入饭团，最多存 5 个 |

豪华值影响单个寿司售价。具体公式、上限、装饰叠加规则未定。建议用可配置的售价倍率，防止经济失衡，但倍率上限属于建议。装修应在场景中确实改变外观，不能只改数值。

通过忙碌和效率瓶颈自然引导玩家购买升级。例如重复点击多次后更愿意买加料升级；顾客增多后更愿意买快煮饭；收入稳定后选择装修。不要用固定天数强制购买来替代这种引导。

## 饮料和饭团

茶与啤酒需要接取，表现杯中液面；清酒直接拿取。啤酒可以表现泡沫，但溢出处罚等额外规则尚未确认。饭团是之后的扩展，最多储存 5 个，不要求首个闭环立即包含整个扩展。

## 昼夜变化

每个营业日随时间在窗外显示缓慢的天色变化。窗框、街景几何和店内对象固定，仅让天空色与窗外亮度逐渐过渡。暂停时冻结天色，下一营业日重新开始。

美术包包含晨光、白天、黄昏和夜晚四张同视角窗外图，以及透明窗洞的固定内景。`assets/09_Docs/day-night.json` 给出预览用关键帧。07:00—22:00 和 40 秒演示周期仅为预览参数，不是已确认的营业长度。

## 暂不加入首版的内容

小偷等额外干扰事件不进入当前首版开发范围。用户对其必要性提出过疑问，当前建议先把厨房经营本身做好；这不是禁止后续讨论。
