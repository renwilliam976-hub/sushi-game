# Codex 开发顺序

## 0. 确认工程环境并开工

检查当前电脑／运行环境和现有工程。若已有项目沿用其结构；若没有，选择适合 iPhone 触控 2D 游戏且当前工具能支持的方案，并向用户解释选择。不要把素材预览页当成已经运行的游戏。

先建立明确的运行步骤、场景入口、营业时钟、暂停和最小存档。将食材、配方、机器、升级、装饰及订单定义为可扩充的数据，具体价格和时长用原型默认值并标注。

## 1. 首个可玩的营业闭环

范围控制在基础米饭、海苔、黄瓜和三文鱼，先用少量配方与顾客。流程必须真实操作：顾客提出订单→煮饭→铺海苔／米饭→点击添加配料→工作台卷切→交付→付款→购买加料效率升级。

同时接入五档库存图、倒车卡车手动补料、窗外昼夜变化、暂停与金币／升级保存。这些是核心手感与视觉表现的一部分，不应完全以文字占位替代。

出餐模块先采用可调整的托盘整单交付建议。明显告知用户这是暂定选择；无需先做两套完整交付玩法。

### 第一阶段验收

- 能从开始营业玩到本日结束，再开始下一日。
- 不同订单可正确匹配制作配方；正确订单满意度为 100%，错误订单按原型评分付款，快速交付有小费。
- 只结算一次，交付后订单状态明确更新。
- 食材用完后不能继续凭空制作，且库存只显示五档贴图。
- 手动补料能看到倒车停靠、开厢、食材入盒、完成后离开的过程。
- 购买加料升级后，重复操作从 3 次减少到 2 次，再可减少到 1 次。
- 买前不显示未解锁的机器；操作区域符合食材盒在中、切配在下。
- 窗外天色缓慢改变；暂停冻结制作与营业时钟，不导致恢复时天空跳变。
- 重启后金币及已购升级仍在；运行说明与实际构建结果吻合。

## 2. 经营成长

加入更多食材位和配方、快煮饭、茶机／啤酒机／清酒、装饰选择与豪华值售价影响。升级界面展示实际收益，例如减少点击次数和缩短煮饭时间；不强制固定天数购买。

每新增一种系统都复用现有订单、库存与数据配置，避免分别编写不兼容的饮料和寿司结算规则。

## 3. 自动化与扩展

加入自动海苔送料／铺饭／卷切、一键自动补料，随后加入五格储存饭团。补齐动画部件、顾客表情切换和音效。

## 4. 适配 iPhone 与发布准备

检查横屏安全区、屏幕比例、触控舒适性、帧率、切图内存和后台恢复。实际使用对应平台工具做构建，并在可用时验证模拟器／真机。用户要求安装时再处理其签名与分发方式，不预先声称已有 iPhone 安装包。

不需要先写一整套抽象测试系统。重点验证订单结算、升级效果、库存／补料、暂停和存档这些可能造成进度或金币错误的环节，以及真实操作手感。
